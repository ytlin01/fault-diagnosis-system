# Route C Case Light RAG v1

## Purpose

TASK-027 adds an optional light-RAG step to the TASK-017 Route C related-case
baseline.

This is not a vector-RAG-first or GraphRAG path. The retrieval order is fixed:

1. lexical/BM25 retrieval over `rag_fp_case_candidates_v1`;
2. optional controlled provider rerank/summary over only the lexical top-k
   candidate projection;
3. unchanged `/api/diagnose` result assembly as candidate related-case output.

The LLM is treated as a reranker/summarizer, not as an evidence source and not
as a selector over the full data estate.

## Source Boundary

The light-RAG adapter can only consume candidates that have already passed the
TASK-017 lexical case index. That index only accepts:

```text
rag_fp_case_candidates_v1 -> case_retrieval
```

It must not read or scan:

- raw data files;
- broad `data/processed/aggregates/` directories;
- `structured_fp_join_v1_baseline` as case RAG input;
- blocked `structured_fp_join_v1_semantic` material.

`structured_fp_join_v1_baseline` remains `fp_review_governance`. It is not
absorbed into the Route C case RAG path.

## Prompt Projection

The provider prompt is built by
`services/retrieval/route_c_case_light_rag.py::build_light_rag_request`.

The projection is a strict subset of TASK-005/TASK-017 allowlisted case fields:

- `rag_candidate_id`
- `source_type`
- `relation_type`
- `route_target`
- `field_fp_variants`
- `field_fp_normalized`
- `RC`
- `PA`
- selected `evidence` summary fields
- `filter_basis.reason`
- lexical rank and lexical score generated by the first-stage BM25 retrieval

The projection excludes source paths, `source_refs`, raw records, debug fields,
unallowlisted fields, and any candidate not returned by lexical top-k.

## Provider Behavior

Light RAG is disabled by default:

```yaml
retrieval:
  route_c:
    case_light_rag:
      enabled: false
      provider_type: stub
```

`stub` mode is deterministic and safe for tests. It does not provide a real
rerank response, so invalid or echo-like provider output falls back to lexical
ranking.

`ollama` and `company_api` modes require explicit light-RAG configuration or an
injected provider. If the provider is unavailable or returns invalid JSON, the
executor keeps lexical ranking and records a warning. It does not change
sources.

Expected provider response:

```json
{
  "ranking": [
    {
      "rag_candidate_id": "RAG_xxx",
      "relevance_reason": "short reason based only on the provided projection"
    }
  ],
  "summaries": {
    "RAG_xxx": "candidate-only relevance summary"
  }
}
```

Unknown candidate IDs are ignored. Missing candidate IDs keep their lexical
relative order.

## Result Behavior

The `/api/diagnose` schema is unchanged. Route C case results remain:

- `result_type=case_reference`
- `status=candidate`
- evidence `source_type=structured_case_candidate`
- evidence `evidence_type=related_case`
- action `source_status=candidate_supported`

Provider text may only contribute a short candidate-only relevance note after
sanitization. It does not become a new evidence source and it cannot promote a
case to reviewed or confirmed diagnosis.

## Benchmark Use

TASK-026 is the comparison gate for this task. The benchmark can run in
lexical-only mode or with the light-RAG stub path:

```text
python scripts/run_eval/run_route_c_case_benchmark_v0.py --compare-light-rag
```

With the default stub provider, quality metrics are expected to match the
lexical baseline. Any claimed quality improvement requires a configured
provider run and must still pass candidate-only and source-safety checks.
